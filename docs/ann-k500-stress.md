# Frozen GPU ANN at k = 500

For the subsequent CPU/GPU profiles and worker improvements, see the
[profiling follow-up](ann-k500-profile.md).

Measured on 2026-11-04, on one host with eight NVIDIA B200 GPUs, 224 logical
CPUs (two Xeon Platinum 8570 sockets) and 2 TiB RAM. PostgreSQL 17.6, extension
0.9.3, cuVS 26.10, GCC 13.3, NVIDIA driver 580.126.09. These are synthetic,
warm-cache measurements on a dedicated test instance, not production SLOs.

## What the fork adds

The frozen `ann` access method keeps key-ordered vectors and attributes,
inverted postings, frequent-value bitmaps and text dictionaries. Immutable
pages are read through read-only mappings; covering scans avoid heap fetches.
The planner translates supported SQL predicates to programs the C GPU worker
evaluates and caches. Generations keep SQL ordinals, exports and worker hits
aligned. The worker batches queries, serves cuVS/CAGRA graphs, and supports
sharding, replication, GPU exact gather scans and Blackwell quantized kernels.
TCP/RDMA and collections extend the same worker to several hosts.

The accompanying correctness changes give each scan its own tombstone copy,
publish worker tombstones after SQL commit with savepoint rollback handling,
guard partition-parent writes with row triggers, and exclude `TABLESAMPLE`
from the custom path. Hot PostgreSQL predicate-cache hits use bounded private
copies without shared-cache locks. Cache keys include the database and explicit
zero padding: GCC structure copies exposed misses when padding was implicit.

This does not make PostgreSQL or the worker entirely lock-free. Mutable TIDs,
visibility maps, relation locking, cache publication/eviction and worker queues
retain synchronization. Existing frozen tables need `ann_freeze(table)` again
after deploying the new library to install their missing row guards.

## Dataset and method

* 10,000,000 rows, 128-dimensional clustered embeddings generated by
  `benchmarks/ann/cuvs_load.py`'s `sample` and `copy_part` helpers, eight load
  jobs with seeds 0–7. Query vectors: 1,000 independent samples, seed 999.
* `tenant = id % 1000`; `category = (id / 7) % 100`, with integer division.
* Permanent table and frozen index in a `/dev/shm` tablespace; temporary sort
  files, exports, CAGRA files and benchmark latency logs also in `/dev/shm`.
  About 21 GiB of tmpfs was used. Heap: 5,851,660,288 bytes; frozen index:
  5,762,555,904 bytes. Cluster control files and WAL stayed on SSD, outside
  the timed read workload. Sampled PostgreSQL/worker physical read bytes were
  zero. The RAM-backed dataset must be recreated after a host reboot.
* One FP16 CAGRA shard replicated on all eight GPUs; FP32 vectors retained for
  reranking and an NVFP4 copy loaded. Do not attribute these k=500 results to
  the specialized top-32 Blackwell selection kernels.
* Filters select approximately 10k, 100k or 1M rows (0.1%, 1%, 10%). The hot
  predicate pool contains 100 tenant equalities, 100 category equalities and
  ten category ranges. All 210 SQL predicate programs are precomputed before SQL timing.
* Each pgbench transaction fetches one query vector and executes one plain
  SQL nearest-neighbor query, returning **500 keys** to the client. Prepared
  protocol, generic plans, up to 32 pgbench threads, one outstanding search
  per client. QPS means nearest-neighbor searches/transactions per second,
  not SQL statements per second. Latency includes the query-vector fetch.
* Concurrency sweeps: 15 seconds per point. Sustained tests: 60 seconds per
  filter. Latency percentiles use a 5% transaction-log sample. No transaction
  failures were reported in the SQL runs below.

```sql
CREATE TABLE frozen_stress
    (id bigint, tenant integer, category integer, emb vector(128))
    WITH (autovacuum_enabled = false) TABLESPACE ram_ann;
-- Load before freezing; see the generator helpers above.
SELECT ann_freeze('frozen_stress');
VACUUM (FREEZE, ANALYZE) frozen_stress;
CREATE INDEX frozen_stress_ann ON frozen_stress USING ann (emb vector_l2_ops)
    INCLUDE (id, tenant, category) WITH (frozen = true) TABLESPACE ram_ann;

-- The 1% workload; the other cases use tenant = $2, or a ten-category range.
SELECT id FROM frozen_stress WHERE category = $2
ORDER BY emb <-> $1::vector LIMIT 500;
```

## Filtered CAGRA baseline

The baseline disables exact CPU and GPU-gather routes, so operation 22 returns
route **1: filtered CAGRA**. This prevents calling an exact scan an ANN result.
Every checked query returned 500 unique hits through `AnnFrozenSearch`, with
no local evaluation. Recall@500 on three queries per filter was 0.928–0.998
(mean 0.988); this small sample is an accuracy check, not a recall guarantee.

| Clients | 0.1% QPS | 1% QPS | 10% QPS |
| ---: | ---: | ---: | ---: |
| 1 | 189 | 366 | 416 |
| 8 | 1,234 | 2,675 | 3,157 |
| 32 | 2,690 | 11,297 | 13,379 |
| 64 | 2,730 | 20,136 | 27,373 |
| 128 | 2,770 | 20,961 | 39,247 |
| 256 | 2,804 | 22,109 | 49,231 |

The 256-client p99 latencies were 134.76, 16.91 and 8.72 ms respectively.
Narrow filters can make graph traversal much more expensive even though fewer
rows are eligible; a GPU gather scan is a better route for those filters here.

Baseline worker settings (set `CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7`):

```sh
ann/server/ann-worker-cuvs --backend cuvs --listen "$SOCKET" \
  --lanes 32 --max-batch 32 --replicate on \
  --itopk 512 --filtered-itopk 1024 --filtered-algo multi --filtered-width 4 \
  --exact-limit 0 --gather-limit 0 --bitset-gather-limit 0 --group-gather-limit 0 \
  --memory-pool 40 --predicate-cache-mb 8192 --predicate-device-mb 16384 \
  --max-pending-mb 8192
```

## Adaptive routing and sustained throughput

Changing only `--gather-limit` to `4000000` and `--bitset-gather-limit` to
`500000` sends the two narrow filters to GPU exact gather scans (route 2).
`--exact-limit 0` still disables exact CPU scans, and `--group-gather-limit 0`
keeps the 10% filter on CAGRA (route 1). These are different algorithms and
are reported separately. The checked narrow-filter results equaled exact SQL
at k=500. The three broad-filter recalls were 0.996, 0.994 and 0.998.

Results with 256 clients, 32 lanes and batches up to 32:

| Selectivity | Route | 60-second QPS | p50 ms | p95 ms | p99 ms | Failed |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 0.1% | GPU exact gather | 33,538 | 7.64 | 10.42 | 11.87 | 0 |
| 1% | GPU exact gather | 29,389 | 8.71 | 12.04 | 13.79 | 0 |
| 10% | Filtered CAGRA | 50,887 | 4.89 | 6.77 | 7.88 | 0 |

## Is PostgreSQL the bottleneck?

A native C client bypassed SQL execution and checked complete 500-hit replies
from the same adaptive worker. It used 256 connections, 20-second windows and
the same query/filter distributions (not identical query/predicate pairs).
Its percentiles sample every twentieth request in 10-microsecond bins.

| Selectivity | SQL QPS | Direct worker QPS | SQL / direct |
| --- | ---: | ---: | ---: |
| 0.1% | 33,538 | 39,817 | 84% |
| 1% | 29,389 | 36,214 | 81% |
| 10% | 50,887 | 95,221 | 53% |

The broad filter has substantial headroom outside PostgreSQL. The direct
comparison includes differences in protocol, query-vector lookup, executor,
tuple/visibility handling, output and worker batch occupancy; it is not a
measurement of one function's cost. Returning `count(*)` around the 500-hit SQL subquery improved the broad
15-second baseline only from 49,231 to 50,848 QPS, so output serialization alone
does not explain the gap.

During the broad sustained run PostgreSQL used CPU time equivalent to about
127 logical CPUs at full utilization, the worker 31, and pgbench 5 (CPU seconds
divided by wall time, summed over the relevant processes). `pg_stat_activity` frequently called a backend
active with no wait event while `/proc/PID/wchan` showed it sleeping in `poll`:
the extension's worker wait is not classified by PostgreSQL's wait reporting.
Use both views before interpreting active backends as CPU-bound.

The host disallowed `perf` (`perf_event_paranoid=4`). Separate debugger runs,
excluded from the throughput tables, sampled user-owned test backends and the
worker. With mmap on, targeted backend snapshots showed worker-reply waits,
TID reads in `AnnArrayLockPage`, and `visibilitymap_get_status` leading into
buffer pins/LWLocks. With mmap off, all four selected snapshots were in buffer
pinning, replacement or LWLock acquisition. These demonstrate paths, not a
statistical breakdown of CPU time. The next read-side work is to reduce/batch
TID and visibility-map accesses while preserving correctness, not to remove
their synchronization blindly.

## Concurrency and lock-avoiding settings

At 256 clients, using the CAGRA baseline:

| Setting | 0.1% QPS | 1% QPS | 10% QPS |
| --- | ---: | ---: | ---: |
| 32 lanes, batch up to 32, mmap on | 2,804 | 22,109 | 49,231 |
| 64 lanes, batch up to 32 | 2,801 | 23,546 | 47,237 |
| 64 lanes, batch size 1 | 2,767 | 22,477 | 46,036 |
| 32 lanes, batch up to 32, mmap off | — | 14,953 | 15,288 |

Mmap improved the broad result by **3.22×** and the 1% result by **1.48×**.
More lanes helped the 1% CAGRA case modestly but increased worker CPU and hurt
the broad case. Thirty-two lanes with batching is the retained configuration;
there is no universal gain from adding concurrency. GPU utilization reported
here is NVML busy time, not SM occupancy.

Disabling `ann.frozen_filter_local_cache_mb` gave 49,237 QPS versus 49,231 with
it enabled. That private cache avoids shared locks for hot **PostgreSQL page
evaluations**; this workload evaluates predicates on the worker, so it is not
the limiting cache. No write locks or mutable-page protections were disabled.

PostgreSQL settings used:

```conf
max_connections = 600
shared_buffers = '4GB'
maintenance_work_mem = '8GB'
work_mem = '64MB'
jit = off
track_io_timing = on
```

Benchmark sessions set `ann.enable_frozen_search=on`, `ann.frozen_mmap=on`,
`ann.frozen_filter_local_cache_mb=16`, `plan_cache_mode=force_generic_plan`, and
`statement_timeout=30000`. The compiled extension and worker enabled RDMA,
but these measurements used Unix sockets, not RDMA.

## Reproducing the measurements

Use a dedicated PostgreSQL 17+ test database with this extension installed and
the cuVS Python builder dependencies. The tested GPU SDK is cuVS 26.10; the
host used CUDA runtime/headers 13.0.96, CRT 13.0.88, NVRTC 13.5.37 and CuPy
14.2. Build the worker with `USE_CUVS=1 USE_RDMA=1` and the extension with
`USE_RDMA=1`, following the [loaded-index guide](ann-cuvs-index.md).

Create a user-owned empty RAM tablespace directory and run `CREATE TABLESPACE
ram_ann LOCATION '/dev/shm/your-empty-directory'`; put the table/index there
and `SET temp_tablespaces='ram_ann'` before building. Generate the permanent
table using `copy_part` (the benchmark's `generate` subcommand creates an
unlogged table and therefore cannot be frozen). Build a query table
`frozen_stress_queries(q integer PRIMARY KEY, v text)` from the 1,000 vectors
returned by `sample(default_rng(999), 1000, 128)`, formatting components with `.6g`.
For example, after creating the empty permanent table and before freezing it:

```sh
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python - <<'PY'
from concurrent.futures import ProcessPoolExecutor
import os, sys
import numpy as np
import psycopg
sys.path.insert(0, 'benchmarks/ann')
from cuvs_load import copy_part, sample
dsn = os.environ['ANN_PG_DSN']
with ProcessPoolExecutor(8) as pool:
    jobs = [pool.submit(copy_part, dsn, 'public.frozen_stress',
                        p * 1250000, 1250000, 128, p) for p in range(8)]
    for job in jobs:
        job.result()
with psycopg.connect(dsn, autocommit=True) as db:
    db.execute('CREATE TABLE frozen_stress_queries (q integer PRIMARY KEY, v text) TABLESPACE ram_ann')
    with db.cursor().copy('COPY frozen_stress_queries FROM STDIN') as writer:
        for i, vector in enumerate(sample(np.random.default_rng(999), 1000, 128), 1):
            writer.write_row((i, '[' + ','.join(f'{x:.6g}' for x in vector) + ']'))
    db.execute('ANALYZE frozen_stress_queries')
PY
```

Then freeze, vacuum and create the index as above. Export and build in RAM:

```sql
SELECT ann_index_export('frozen_stress_ann', '/dev/shm/your-run/export');
```

```sh
python ann/builder/build_cuvs_index.py --from-export /dev/shm/your-run/export \
  --out /dev/shm/your-run/index --shards 1 --dtype float16 --quantize nvfp4
```

Load under `frozen_stress` with `ann_index_load`, precompute the 210 filters
using `ann_frozen_precompute`, and check EXPLAIN reports `AnnFrozenSearch`, the
expected worker, one worker call and zero local evaluations. Verify operation
22's route code and recall against exact SQL before timing. Monitor tools
require Linux `/proc`, `nvidia-smi`, NumPy, psycopg and pgbench:

```sh
export ANN_PG_DSN='host=/your/socket/directory port=55439 dbname=gpu_ann'
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --clients 1,8,32,64,128,256 --seconds 15 --k 500
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --label sustained --clients 256 --seconds 60 --k 500

# Native worker control: all timed request handling is C.
cc -O2 -std=c11 -pthread benchmarks/ann/frozen_direct.c -o /tmp/frozen-direct
python benchmarks/ann/frozen_direct.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --binary /tmp/frozen-direct --output results --label direct-adaptive --seconds 20

# Diagnostic controls, run separately:
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --label mmap-off --clients 256 --workloads 1pct,10pct --mmap off
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --label count --clients 256 --workloads 10pct --count-only
```

The driver saves pgbench output and per-run JSON containing QPS, sampled
percentiles, CPU seconds, physical I/O bytes, PostgreSQL wait samples, OS wait
channels and per-GPU busy-time samples. For targeted debugger sessions on a
Yama-restricted test host, compile `benchmarks/ann/profile_backend.c` as a shared
library against the server headers and pass its absolute path without `.so`
as `--profile-library`. It enables same-user debugger attachment only in those
sessions; it changes no host-wide perf/ptrace settings. Exclude debugger runs
from performance comparisons.

## Planner-costing follow-up

After replacing the frozen path's fixed cost with normal startup and per-row
costs, the same 10M-row dataset and adaptive worker were tested again at
`ann.frozen_setup_cost = 1000`, k=500 and 256 clients. Each mode/filter ran for
60 seconds, fetching the query vector and returning all 500 keys. Prepared
EXPLAINs confirmed `AnnFrozenSearch` for all three filters with both generic
plans and parameter-specific custom plans. Separate EXPLAIN ANALYZE checks
confirmed 500 rows, one worker call, zero local evaluations and zero heap
fetches for each filter at the default setup cost.

| Selectivity | Generic plan QPS | Custom plan QPS | Generic p99 ms | Custom p99 ms |
| ---: | ---: | ---: | ---: | ---: |
| 0.1% | 33,253 | 33,021 | 12.03 | 12.10 |
| 1% | 29,684 | 29,649 | 13.40 | 13.44 |
| 10% | 50,850 | 49,854 | 7.89 | 8.14 |

All 13,549,355 transactions succeeded; monitoring reported no errors and zero
sampled physical read bytes. Generic-plan rates were within approximately 1%
of the earlier sustained measurements. Custom planning showed no throughput
benefit here and was about 2% slower for the broad filter. These are single,
sequential runs per mode/filter, so small differences are not evidence of a
repeatable improvement or regression. The costing change lets selective local
plans compete; it does not speed up a workload that retains the same GPU path.

The broad-filter generic run consumed about 127 PostgreSQL CPU cores versus
31 worker cores on average. Together with the earlier 95,221 direct-worker
QPS control and sampled buffer/visibility-map stacks, this points to substantial
PostgreSQL overhead for broad filters. Narrow filters remain closer to their
earlier direct-worker limits of 39,817 and 36,214 QPS. The direct controls were
not repeated in this follow-up; they exclude SQL planning, vector lookup and
tuple processing, and are not a pure measurement of planner overhead.

Reproduce the two modes separately with the same loaded worker:

```sh
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --label costed-generic --clients 256 --seconds 60 --k 500 \
  --setup-cost 1000 --plan-cache-mode force_generic_plan
python benchmarks/ann/frozen_stress.py --socket "$SOCKET" --worker-pid "$WORKER_PID" \
  --output results --label costed-custom --clients 256 --seconds 60 --k 500 \
  --setup-cost 1000 --plan-cache-mode force_custom_plan
```

Full metrics and prepared plans are in the
[planner-costing result artifact](../benchmarks/ann/results/frozen-k500-planner-costing.json).
The GPU node also passed all 27 frozen tests (including GPU k=500 rollback and
deletion) and all 16 SQL regression tests after a clean rebuild.

## Reusing visibility-map pins

The broad-filter profiles led to a concrete read-side change: retain up to 32
visibility-map buffer pins per frozen scan instead of just one. Distance-ordered
hits move between heap blocks and previously forced frequent VM buffer lookups
and pin/unpin operations. A bounded direct-mapped array now reuses the pins;
every tuple still checks its current visibility bit, mutable TIDs still use
shared buffer locks, and non-all-visible pages still use snapshot-aware heap
fetches. All pins are released at scan end.

At the same default setup cost, 256 clients and k=500, 60-second 10% runs gave:

| Run | QPS | p99 ms | PostgreSQL CPU cores | Worker CPU cores |
| --- | ---: | ---: | ---: | ---: |
| 32 pins, first run | 65,053 | 6.66 | 64.2 | 32.5 |
| One-pin control | 50,888 | 7.94 | 126.9 | 30.6 |
| 32 pins, repeat | 65,053 | 6.69 | 64.3 | 32.5 |

The control compiled the same implementation with its cache size set to one,
then restored the 32-pin build before repeating. Pin reuse increased throughput
by 27.8%, reduced PostgreSQL CPU use by about half, and cut p99 by about 16%.
Thirty-second narrow-filter checks reached 33,276 QPS at 0.1% and 29,507 QPS
at 1%, close to the earlier results. All 12,727,069 transactions across these
five runs succeeded, with no monitor errors and zero sampled physical reads.
The worker and GPU routing settings were unchanged.

The implementation passed all 27 frozen tests including GPU k=500 deletion
and rollback, all 16 SQL regressions, macOS/Linux builds and pgindent. Full
metrics are in the [VM-pin result artifact](../benchmarks/ann/results/frozen-k500-vm-pins.json).
This improves one measured source of PostgreSQL overhead; it does not establish
that TID access, tuple execution or result transport are no longer bottlenecks.

The earlier run also passed 15 GPU tests, the CPU/PostgreSQL integration suites and
all 16 SQL regression cases. The GPU frozen test now includes rollback and
committed deletion checks at k=500. Selected measured results and correctness
samples are in [the result artifact](../benchmarks/ann/results/frozen-k500-2026-11-04.json).
